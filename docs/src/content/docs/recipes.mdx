## Recipe 1: headless rendering in a CLI/CI job

Parse, lay out, and emit SVG in one call — no browser, no jsdom, DOM-free (though it does
need `react`/`react-dom` installed; see [Architecture](../architecture/#why-isnt-server-part-of-core)
for why).

```ts
import { renderC4DiagramToSVG } from '@liminis/diagrams/server';

const source = `
Person(user, "User", "End user")
System(app, "App", "Main app")
Rel(user, app, "Uses", "HTTPS")
`;

const { svg, errors } = renderC4DiagramToSVG(source, /* isDarkMode */ false);

if (errors.length > 0) {
  console.error(errors);
  process.exit(1);
}

console.log(svg);
```

**Verified output** (`errors` is `[]`; `svg` is 1762 characters):

```html
<svg width="320" height="394" viewBox="0 0 320 394" xmlns="http://www.w3.org/2000/svg" data-diagram="c4" style="font-family:system-ui, -apple-system, sans-serif"><g class="boundaries-layer"></g><g class="nodes-layer"><g><circle cx="160" cy="66" r="14" fill="#006b2d" stroke="#004b1e" stroke-width="1...
```

If `parseC4` or `validateC4` fail internally, `renderC4DiagramToSVG` returns `{ svg: '',
errors }` rather than throwing — always check `errors` before using `svg`.

## Recipe 2: embedding `C4InteractiveRenderer` in a non-editor host

`C4InteractiveRenderer` is a **controlled component**: it takes `manualPositions` in
as a prop and calls `onPositionChange` out during/after a drag. It holds no persisted
state of its own — the host owns `manualPositions` and decides what to do when the
callback fires (nothing, `useState`, write to disk, debounce a network call, etc.).

```tsx
import { useState } from 'react';
import { parseC4 } from '@liminis/diagrams/core';
import { C4InteractiveRenderer } from '@liminis/diagrams/react';

function DiagramHost({ source }: { source: string }) {
  const { diagram } = parseC4(source);
  const [positions, setPositions] = useState<Record<string, { x: number; y: number }>>({});

  if (!diagram) return null;

  return (
    <C4InteractiveRenderer
      diagram={diagram}
      isDarkMode={false}
      isEditMode={true}
      manualPositions={positions}
      onPositionChange={setPositions}
    />
  );
}
```

With `manualPositions={{}}` (nothing set yet), the renderer lays the diagram out with
dagre and lets you drag any node; each drag calls `onPositionChange` with the *complete*
new positions map (not just the moved node — the first drag also seeds every other
node's current auto-layout position into the map, so `manualPositions` after any drag is
enough on its own to reproduce the layout without dagre).

**Verified**: rendering `DiagramHost` with `isEditMode={true}` produces one draggable
hit area (an `SVGRectElement` with `data-node-id`) per top-level and nested node — for a
two-element diagram (`user`, `app`), `container.querySelectorAll('[data-node-id]')`
returns exactly `['user', 'app']`. Passing `manualPositions={{ user: { x: 500, y: 500 },
app: { x: 900, y: 500 } }}` and re-rendering places `user`'s hit area at exactly `x="500"
y="500"` in the rendered SVG — confirming positions flow from the host's state straight
through to what's drawn, with no intermediate transformation.

## Recipe 3: position persistence — the host's choice

This package never writes anything to disk, a database, or anywhere else. `manualPositions`
is a plain `Record<string, { x: number; y: number }>` — how you store it is entirely up
to you. The simplest possible approach is to serialize it as JSON:

```ts
const positions = { user: { x: 10, y: 20 }, app: { x: 300, y: 20 } };
const stored = JSON.stringify(positions);
// stored: '{"user":{"x":10,"y":20},"app":{"x":300,"y":20}}'

// ...later, from wherever you stored `stored`...
const restored: Record<string, { x: number; y: number }> = JSON.parse(stored);
// restored deep-equals positions — verified round-trip
```

Pass `restored` back in as `manualPositions` (Recipe 2) or as the third argument to
`layoutC4Diagram` (Recipe 1's lower-level building block) to render with the saved
layout instead of dagre's auto-layout.

### One worked example: how `@liminis/editor` does it

**This is `@liminis/editor`'s own decision, not something `@liminis/diagrams` does or
requires.** It's included here as one concrete answer to "where would I actually put
this," not as this package's behavior.

`@liminis/editor` stores positions in the **meta string of the markdown code fence**
that holds the C4 source — the same place a fenced code block's language tag lives,
as the text following the language on the fence's opening line (e.g. the part after
`c4 ` in an opening fence tagged `c4`). On write, if there are any manual positions, it
serializes them as `@layout ` followed by JSON:

```ts
// verveguy/liminis-editor, src/app/mapper/lexicalToMdast.ts — convertC4Node()
const manualLayout = node.getManualLayout();       // { positions: {...} } | undefined
const meta = manualLayout && Object.keys(manualLayout.positions).length > 0
  ? '@layout ' + JSON.stringify(manualLayout)
  : undefined;
```

producing a fence meta string like:

```
@layout {"positions":{"user":{"x":10,"y":20},"app":{"x":300,"y":20}}}
```

On read, `src/app/mapper/mdastToLexical.ts`'s `extractC4LayoutFromMeta` looks for the
`@layout ` prefix, `JSON.parse`s the rest, and validates every position has finite
numeric `x`/`y` before trusting it — falling back to `undefined` (auto-layout) on
anything malformed:

```ts
function extractC4LayoutFromMeta(meta: string | null | undefined): ManualLayout | undefined {
  if (!meta?.startsWith('@layout ')) return undefined;
  try {
    const raw = JSON.parse(meta.slice('@layout '.length));
    // ...validates raw.positions[key].x/.y are finite numbers...
    return raw as ManualLayout;
  } catch {
    return undefined;
  }
}
```

**Verified**: the round-trip `'@layout ' + JSON.stringify({ positions }) →
meta.slice('@layout '.length) → JSON.parse(...)` reproduces the original `positions`
object exactly, for the example above.

The advantage of this approach, specific to `@liminis/editor`'s context: it keeps a
hand-arranged diagram's positions in the same plain-text, line-diffable markdown file as
the diagram source, with no sidecar file and no binary blob. If your host isn't a
markdown editor, this is not the right storage format for you — pick whatever fits your
host (a database column, a separate JSON file next to the source, a CRDT document,
whatever). The only contract this package cares about is the shape:
`Record<string, { x: number; y: number }>`.

## Recipe 4: adding elements and relationships — the host's responsibilities

> Available from the release after 0.1.6. The docs-site playground and the demo are
> pinned to the published package, so they do not show this yet.

The renderer can add things; **it never changes your source and never writes anywhere**.
It *reports* an edit, you apply it. This is the same controlled pattern as
`onPositionChange`, and it means undo, persistence and conflict handling are whatever
your host already has.

In edit mode, **and only when you pass `onEdit`**, `C4InteractiveRenderer` offers three
things. (A host that passes `isEditMode` for dragging alone sees no change at all.)

- **Add an element.** Right-click empty canvas — or inside a boundary to add it there — to
  open a menu of kinds (Person, System, Container, Component, and the `Db` variant of
  System, Container and Component). On touch, which has no right-click, **press and hold
  for about half a second** without moving: the same menu opens. Moving the finger
  further than a few pixels cancels the press, so a drag never opens a menu. Choosing a
  kind places the element at the point you opened the menu, then a label input appears
  over it. Enter confirms (an empty label falls back to a placeholder); Escape or losing
  focus cancels and reports nothing. The menu itself closes on Escape, a click outside it,
  or `pointercancel` of the pointer that opened it, and reports nothing. While editing is
  on the browser's own context menu is suppressed over the diagram; a read-only render,
  and a host that passes `isEditMode` without `onEdit`, keep it.
- **Add a boundary.** The same menu has a second group, set apart by a rule and a small
  heading, listing the boundary kinds: System boundary, Container boundary and Boundary
  (`System_Boundary`, `Container_Boundary`, `Boundary`). The label flow is the same as for
  an element. It adds an **empty** boundary where you opened the menu: at top level on
  empty canvas, or nested in the innermost boundary containing the point. An empty boundary
  is drawn as a visible, dashed box (at least 240×160), so you can right-click inside it and
  add an element, or another boundary, with the flow above. A boundary nested inside another
  is kept within its parent's content area, so the parent does not move. Boundaries have no
  connect handle and cannot be relationship endpoints. Wrapping existing elements in a new
  boundary is not offered.
- **Add a relationship.** Drag from the dot on an element's right edge to another
  element. On release a label input appears near the midpoint of the new edge, pre-filled
  with "Uses": Enter confirms (empty falls back to "Uses"), Escape or losing focus cancels
  and reports nothing, and the source is untouched until then. Releasing on empty canvas,
  on a boundary, or on the same element shows no input and reports nothing. Boundaries
  cannot start or end a relationship in this first cut. This labels the *new* `Rel` only;
  renaming an existing element or relationship is not offered.

The menu opens over empty canvas or a boundary, not over an element, a connect handle or
the legend (the native menu is still suppressed there).

Dragging a node still moves it; the connect handle is a separate target, and the two
gestures are mutually exclusive. All of it uses pointer events and handles
`pointercancel`. The handle sits on each node's right edge with a touch target of about
16 SVG units, so the strip of a node just inside its right edge starts a connection
rather than a move; grab the node anywhere else to move it.

### The host's half

`onEdit(edit, { positions })` gives you two things, and you must do both **in the same
update**:

1. **Apply `edit` to your source text** with `applyC4Edit` from `./core`. It is headless —
   no React — so the same call works from a test, a CLI or an agent.
2. **Store `positions`**, replacing your own map. It is already the merge you want:
   your current manual positions (untouched), plus the current position of every node that
   had none, plus the new element at the spot the user placed it. Pinning every visible
   node is what stops the automatic layout reshuffling when a node is added.
   **Merge, don't clear.** A host that resets its layout whenever the set of element ids
   changes (as `@liminis/editor`'s `C4Component.tsx` does today) throws away every
   arranged position the moment one box is added; that behaviour has to become a merge
   before this feature is usable there.

Apply both together. If the new text lands a frame before the new positions, the diagram
renders the new element at the bottom of the stacked column and then jumps. In a plain
`useState` host this is free (React batches two setters in one handler); in a host that
updates asynchronously, make sure the two arrive in one update.

```tsx
import { useState } from 'react';
import { parseC4, validateC4, applyC4Edit } from '@liminis/diagrams/core';
import { C4InteractiveRenderer } from '@liminis/diagrams/react';
import type { C4Edit } from '@liminis/diagrams/core';
import type { C4EditContext } from '@liminis/diagrams/react';

function EditableDiagram({ initial }: { initial: string }) {
  const [text, setText] = useState(initial);
  const [positions, setPositions] = useState<Record<string, { x: number; y: number }>>({});
  const [error, setError] = useState<string | null>(null);

  const parsed = parseC4(text);
  const errors = parsed.diagram ? validateC4(parsed.diagram) : parsed.errors;
  // Nothing to click while the text does not parse, so editing is unavailable.
  if (!parsed.diagram || errors.length > 0) return <pre>{text}</pre>;

  const onEdit = (edit: C4Edit, context: C4EditContext) => {
    const result = applyC4Edit(text, edit);
    if (!result.ok) {
      setError(result.message); // e.g. a boundary that cannot take a new line
      return;
    }
    setError(null);
    setText(result.source);          // 1. the new source text...
    setPositions(context.positions); // 2. ...and the merged positions, in the same update
  };

  return (
    <>
      {error && <p role="alert">{error}</p>}
      <C4InteractiveRenderer
        diagram={parsed.diagram}
        isDarkMode={false}
        isEditMode
        manualPositions={positions}
        onPositionChange={setPositions}
        onEdit={onEdit}
      />
    </>
  );
}
```

This is `C4Playground`'s own wiring, and the playground's end-to-end test
(`src/playground/C4Playground.test.tsx`) drives exactly this: add a top-level element,
add an element inside a boundary, add a boundary and then an element inside it, connect two
elements, diffing the source each time.

**Verified** by that test: each action inserts exactly one contiguous block (one line, or
two for a boundary) and no other line changes; previously positioned elements keep their positions; the first edit on a diagram
with no manual positions moves no element.

### `applyC4Edit`, headless

```ts
import { applyC4Edit } from '@liminis/diagrams/core';

const source = `@startuml
Person(user, "User")
System(app, "App")
Rel_D(user, app, "Uses", "HTTPS")
@enduml`;

const r = applyC4Edit(source, { kind: 'add-element', elementKind: 'system', label: 'Billing' });
// r = { ok: true, source: <...>, insertedLine: 'System(billing, "Billing")', label: 'Billing', alias: 'billing' }
```

The result source is the input with one line (or, for `add-boundary`, one two-line block) inserted after the last top-level element or
boundary (wherever that sits relative to any `Rel` lines, and always before `@enduml`). An element with `parent` set to a
boundary id goes inside that boundary's `{ ... }` block, indented like its siblings. A
`add-relationship` edit inserts one `Rel(source, target, "label")` line after the last
top-level `Rel`.

`add-boundary` adds an empty boundary, the one edit that inserts more than a single line:
an opening line and a closing `}`, **together at one point**. "Exactly one line" is
therefore "exactly one contiguous block" for this kind only; no existing line changes.

```ts
const b = applyC4Edit(source, { kind: 'add-boundary', boundaryKind: 'containerBoundary', label: 'API Application' });
// b = { ok: true, source: <...>, label: 'API Application', alias: 'api_application',
//       insertedLine: 'Container_Boundary(api_application, "API Application") {',
//       insertedLines: ['Container_Boundary(api_application, "API Application") {', '}'] }

// The new boundary can take children straight away:
applyC4Edit(b.source, { kind: 'add-element', elementKind: 'component', label: 'Controller', parent: 'api_application' });
```

`boundaryKind` is `systemBoundary`, `containerBoundary` or `boundary`; `parent` nests it in
an existing boundary. Alias, label, indentation and the error codes behave exactly as for
`add-element`, and the closing `}` is aligned with the opening line. Every successful
result carries `insertedLines` (one element for the other kinds); `insertedLine` is the
first of them.

Failures are returned, not thrown: `{ ok: false, code, message }`, where `code` is one of
`parse-error`, `unknown-parent`, `unknown-endpoint`, `boundary-cannot-take-children`
(a boundary with no braces, a single-line `{ }`, or an unterminated block: adding a child
would mean rewriting an existing line), `alias-collision`, `invalid-alias`,
`self-relationship`, `invalid-result`.

Four guarantees worth relying on:

- **The source stays canonical.** An edit is an insertion (one line, or one two-line block
  for a boundary) at a character offset. No
  existing byte changes: comments, `Rel` technology arguments, `Rel_D`-style variants,
  `!include`, `title`, `SHOW_LEGEND()` and `LAYOUT_*` all survive, and CRLF files get CRLF.
  The parsed model is lossy and is never re-serialised.
- **The result parses.** Every returned source is re-parsed before it is returned.
- **Aliases are unique and valid.** Without `alias` one is generated from the label
  (`Cache` → `cache`, then `cache_2`, …), avoiding every existing id, macro names and the
  reserved `__legend__`. The renderer decides the alias itself because positions are keyed
  by it; if you pass one and it collides with your current text, you get
  `alias-collision` rather than a silent rename (which would orphan the position).
- **Labels are made safe, not rejected.** The parser does not un-escape and PlantUML has
  no escape for `"`, so inside a quoted argument `"` becomes `'`, `\` becomes `/`, and
  control characters become spaces. The result reports the label as written.

### Styling the menu

The add menu is the package's only built-in control. It uses inline styles and
reads `--c4-accent`, `--c4-border` and `--c4-bg`, and it carries `data-c4-menu` for
targeting. It has two `role="group"`s: element items carry `data-kind`, boundary items
carry `data-boundary-kind`. It replaces the toolbar palette (`data-c4-palette`)
of earlier drafts, which no longer exists. The inline label inputs — for an element and
for a relationship, and for a boundary — carry `data-c4-label-input`.
